## The config

`~/.config/duckwm/config.lua` is ordinary Lua, run once at startup and again
on every reload. It talks to duckwm through the global `wm` table. A reload
starts a fresh Lua VM: keys, rules and Lua state from the last run are gone,
and windows are laid out again by the arrangers the new config sets.

If the config fails to load, duckwm shows the error and runs
`/etc/duckwm/config.lua` instead. That file is a complete config in itself and
a good starting point: copy it and change what you like.

```lua
local M, S = wm.MOD_SUPER, wm.MOD_SHIFT

wm.set_border_width(2)
wm.set_gaps(4, 4, 8, 8)
wm.set_workspace_switch_mode("previous")
wm.exec_once({ "dunst" }) -- at startup only, not on reloads
```

`wm.PLATFORM` is `wm.PLATFORM_X11` or `wm.PLATFORM_RIVER`, for the few things
that differ between the two (which terminal to start, environment variables).

## Keys

`wm.bind(mods, key, fn)` calls `fn` with no arguments when the key is pressed.
Keys are xkb keysym names: `"Return"`, `"h"`, `"F11"`, `"comma"`.

```lua
wm.bind(M, "Return", function() wm.spawn({ "foot" }) end)
wm.bind(M | S, "q", wm.kill_client)

for i = 1, 9 do
	wm.bind(M, tostring(i), function() wm.switch_to_workspace(i) end)
end
```

Keys bound inside an arranger factory (see below) belong to that workspace,
and win over global keys there.

## Rules

A rule is a function called for every window, whatever the layout. It gets
an event and the window's id:

- `"pre_map"`: before the window is placed, the moment to float it or make it
  fullscreen
- `"map"`: after it's placed
- `"unmap"`: it's leaving the layout (closed, floated or moved away)
- `"prop"`: its class or title changed, for apps that set them late

```lua
wm.add_rule(function(event, id)
	if event ~= "pre_map" then return end
	local class = wm.get_window_class(id)
	if class == "pavucontrol" then
		wm.set_floating(id, true)
	end
end)
```

## Transactions

Every event duckwm handles (a key, a new window, an IPC command) runs as one
transaction. If a callback raises an error, or what it leaves behind doesn't
validate, everything it changed is undone. A broken key binding can't leave
half a layout behind.

You can make your own transactions inside Lua:

```lua
wm.transaction(function()
	wm.send_to_workspace(id, 2)
	wm.switch_to_workspace(2)
	-- return false (or raise an error) and neither happened
end)
```

## The prompt

`wm.read_line(prompt, fn)` opens a one-line input bar, StumpWM style, and
calls `fn` with the text on Enter. Escape cancels. `wm.set_prompt_keys("vi")`
switches its editing keys from emacs to vi. `wm.message(text, ms)` shows text
in the same bar.

```lua
-- Run a command
wm.bind(M, "r", function()
	wm.read_line("run: ", function(cmd) wm.spawn({ "sh", "-c", cmd }) end)
end)

-- Evaluate Lua in the running WM
wm.bind(M | wm.MOD_CTRL, "p", function()
	wm.read_line("lua: ", function(src)
		local _, out = wm.eval(src)
		wm.message(out, 4000)
	end)
end)
```

`quack repl` gives you the same evaluator from a terminal.

## How layouts work

A layout is an **arranger**: a function duckwm calls whenever something
happens on a workspace. It gets a snapshot of the workspace and returns the
whole layout as data. duckwm turns that into constraints, solves them and
moves the windows.

### Setting one

`wm.set_arranger(factory, name)` sets the current workspace's layout, and
`wm.set_default_arranger(factory, name)` the one new workspaces get. A
**factory** is a function that returns the arranger; duckwm calls it once per
workspace.

```lua
local function factory()
	return function(event, id, prev_id, s)
		-- s is the snapshot; return the layout and the state to keep
		return { nodes = {} }, nil
	end
end
wm.set_default_arranger(factory, "mine")
```

### The snapshot

| Field                        | What it is                                                                                       |
| ---------------------------- | ------------------------------------------------------------------------------------------------ |
| `s.event`                    | `"map"`, `"unmap"`, `"resize"`, `"focus"`, `"pre_map"`, or `"area"` (the work area changed size) |
| `s.id`                       | the window the event is about                                                                    |
| `s.prev_id`                  | the window focused before it, or nil; a new window usually opens next to it                      |
| `s.work_area`                | `{ x, y, width, height }` of the area to tile                                                    |
| `s.windows`                  | the tiled windows: `{ id, geometry = { x, y, width, height } }`                                  |
| `s.focused`                  | the focused window's id, or nil                                                                  |
| `s.cursor_dx`, `s.cursor_dy` | the pointer's offset from the focused window's centre                                            |
| `s.layout`                   | the layout as duckwm has it now, including the user's resizes                                    |
| `s.state`                    | what this arranger returned as state last time on this workspace, or nil                         |

On `"unmap"`, `s.windows` still includes the window that's leaving, so skip
`s.id` there.

### The reply

The arranger returns two things:

1. **The layout:** `{ nodes = { ... } }`, or nil to leave the layout as it is.
   Each node is `{ id = ..., constraints = { ... } }`. It replaces the
   workspace's layout as a whole.
2. **The state** to keep for next time, any Lua value made of tables, strings,
   numbers and booleans. nil keeps the old state.

A node's `id` is a window id, or `{ key = k }` for a **container**: a box with
no window that other nodes are placed in. duckwm creates a container the first
time a layout names its key, and removes it once a layout leaves it out.

Constraint coordinates are relative to the work area's corner, so a layout
works the same on every monitor and with any bar. The ones most layouts need:

| Constraint                                                                                 | Meaning                                                               |
| ------------------------------------------------------------------------------------------ | --------------------------------------------------------------------- |
| `{ type = "fixed_x", value = x }` (also `fixed_y`, `fixed_width`, `fixed_height`)          | an exact position or size                                             |
| `{ type = "grid_cell_abs", container = c, x = .., y = .., w = .., h = .. }`                | a rectangle inside container `c`                                      |
| `{ type = "split", container = c, axis = "h" or "v", children = { .. }, ratios = { .. } }` | `c` divided into its children side by side (`"h"`) or stacked (`"v"`) |

A split's ratios are where resizing ends up: drag the border between two
windows and duckwm changes the ratios. The next time the arranger runs, it
finds them in `s.layout` and can keep them. The others are in `API.md`.

## Tutorial: a master-and-stack layout

The goal: the first window takes the left 60% of the screen, and the others
share the right side, one above the other. Resizes stick.

### 1. The windows to lay out

Every arranger starts the same way: which windows are tiled, minus the one
leaving.

```lua
local function windows(s)
	local out = {}
	for _, w in ipairs(s.windows) do
		if not (s.event == "unmap" and w.id == s.id) then
			out[#out + 1] = w.id
		end
	end
	return out
end
```

### 2. One window

With nothing else to share with, a window gets the whole area. A container
with fixed bounds holds it, so step 3 can split that container.

```lua
local function fill(w, h)
	return {
		{ type = "fixed_x", value = 0 },
		{ type = "fixed_y", value = 0 },
		{ type = "fixed_width", value = w },
		{ type = "fixed_height", value = h },
	}
end

local function tall(s)
	local ws = windows(s)
	local W, H = s.work_area.width, s.work_area.height
	if #ws == 0 then
		return { nodes = {} }
	end
	if #ws == 1 then
		return { nodes = { { id = ws[1], constraints = fill(W, H) } } }
	end
	-- step 3
end
```

### 3. Master and stack

Two containers. The root, key 0, fills the area and is split side by side
into the master window and a second container, key 1. That one is split top
to bottom among the rest. Each window also gets a node of its own, with no
constraints: the splits place it.

```lua
	local stack = {}
	for i = 2, #ws do
		stack[#stack + 1] = ws[i]
	end

	local root = fill(W, H)
	root[#root + 1] = {
		type = "split", container = { key = 0 }, axis = "h",
		children = { ws[1], { key = 1 } }, ratios = { 0.6, 0.4 },
	}
	local nodes = {
		{ id = { key = 0 }, constraints = root },
		{ id = { key = 1 }, constraints = {
			{ type = "split", container = { key = 1 }, axis = "v", children = stack },
		} },
	}
	for _, w in ipairs(ws) do
		nodes[#nodes + 1] = { id = w, constraints = {} }
	end
	return { nodes = nodes }
```

Without `ratios`, a split shares its space equally.

### 4. Keep the user's resizes

As it is, dragging the master's edge works until the next window opens: then
the layout runs again and puts back 0.6 and 0.4. The ratios duckwm has now are
in `s.layout`; use them when they're there.

```lua
local function ratios_of(s, key)
	for _, n in ipairs((s.layout or {}).nodes or {}) do
		if type(n.id) == "table" and n.id.key == key then
			for _, c in ipairs(n.constraints or {}) do
				if c.type == "split" then
					return c.ratios
				end
			end
		end
	end
end
```

In step 3, use the stored ratios when there are two of them:

```lua
	local kept = ratios_of(s, 0)
	local ratios = (kept and #kept == 2) and kept or { 0.6, 0.4 }
```

and pass `ratios = ratios` in the root's split. The stack's split can do the
same with key 1, as long as the count matches `#stack`.

### 5. State: a master that stays put

`s.windows` comes in duckwm's order, which may not be the order you want. To
make the first window opened stay the master, remember the order yourself.
Return it as the state, and read it back from `s.state`:

```lua
local function order(s)
	local present, out = {}, {}
	for _, w in ipairs(windows(s)) do
		present[w] = true
	end
	for _, w in ipairs(type(s.state) == "table" and s.state or {}) do
		if present[w] then
			out[#out + 1] = w
			present[w] = nil
		end
	end
	for _, w in ipairs(windows(s)) do -- new windows at the end
		if present[w] then
			out[#out + 1] = w
		end
	end
	return out
end
```

In `tall`, use `local ws = order(s)` instead of `windows(s)`, and return the
order as the second value everywhere: `return { nodes = nodes }, ws`. The
state is kept per workspace, so each one has its own master.

Check that the state is the shape you expect before using it, as `order`
does. Then a state from an older version of your layout can't break it.

### 6. Focus new windows

duckwm doesn't move focus to a new window by itself; the layout decides.
Before returning:

```lua
	if s.event == "map" then
		wm.focus(s.id)
	end
```

### 7. Use it

```lua
local function factory()
	return function(_, _, _, s)
		return tall(s)
	end
end

wm.bind(wm.MOD_SUPER, "m", function() wm.set_arranger(factory, "tall") end)
```

If the arranger raises an error, the event's changes are undone and the error
is printed. The default config's layouts are worth reading next: they handle
more cases (where the cursor is, a direction per window, a canvas wider than
the screen) in the same style.

## Split-direction indicators

An indicator is one side of a window's border drawn in a highlight colour, to
show where the next window will open. Set the colour once, then move the
indicator as focus moves. The `"focus"` event is the place for that:

```lua
wm.set_indicator_color(0xf9e2af)

-- inside an arranger, with ids the windows it lays out:
local function indicate(ids, focused, side)
	for _, w in ipairs(ids) do
		if w ~= focused then
			wm.clear_node_indicator(w)
		end
	end
	if focused then
		wm.set_node_indicator(focused, side) -- "right" or "bottom"
	end
end
```

Call `indicate` on `"map"` and `"focus"` with `s.id`, and on `"unmap"` with
the window that takes focus. By default indicators show only on the focused
window; `wm.set_border_side_colors_focused_only(false)` shows them on every
window. The default config's scroller2d and manual layouts keep a direction
per window this way, switched with Super+T.

## Multiple monitors

Each monitor has its own workspaces, i3 style. Commands act on the focused
monitor: `switch_to_workspace(2)` is workspace 2 of the monitor you're on.

- `wm.focus_output(dir)` and `wm.send_to_output(id, dir)` move focus, or a
  window, to the monitor in a direction (`"left"`, `"right"`, `"up"`,
  `"down"`).
- Directional focus (`wm.focus_left()` and the others) carries on onto the
  next monitor when there's nothing further on this one.
- `wm.get_outputs()` lists the monitors with their positions and sizes.

Arrangers need nothing special: each runs for its own workspace, with that
monitor's work area.
